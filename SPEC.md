# Micro Gmail backup

Implementation contract. Implementation requested on 2026-10-29.

## Minimal design

Simplicity is the guiding design principle: use the smallest clear implementation that satisfies the required behavior. Around 100 lines indicates the intended scale, not a limit or a target. Every function, class, branch, stored field, and dependency must earn its place by making the required behavior simpler to implement, understand, or verify. Prefer removing unnecessary state and abstractions over shortening syntax. Use normal readable Python formatted by Black.

Start with one Python script, `micro_gmail_backup.py`. Functions, classes, and dataclasses are all available when they simplify the solution; none is mandatory merely to satisfy a structural convention. Do not introduce a package, framework, or extra layer without a concrete simplification. Follow `../my-agent-rules/generic-coding-rules.md` (private), with this simplicity principle taking precedence over prescriptive structural recommendations. Keep functions typed and runtime-checked with beartype; for a single script, use `@beartype`. Message metadata is a dataclass with a from_dict classmethod: beartype checks the types, __post_init__ checks the values, and from_dict rejects extra keys.

Prefer direct dict key access and `assert` statements for validation; let unexpected errors crash the script with a traceback instead of building custom exception plumbing. Do not catch broad `Exception` or `OSError` to recover or continue: local disk failures are unrecoverable, so they crash with a traceback like everything else. The one allowed broad handler is at the entry point: it only logs the traceback, so it reaches the file log too, and exits nonzero. Do not pre-validate what the next operation already rejects (for example, no magic-byte pre-check when decompression itself rejects bad input). Body completeness (every frame complete up to the end of the file, no truncation or trailing data) must still fail loudly, via the decompressor's own end-of-frame signal. Any valid Zstandard layout verifies, single or multiple frames, so bodies may be recompressed later; the SHA-256 decides integrity. Format for readability with blank lines between logical steps; never remove blank lines to look shorter.

Name functions and module constants normally; do not prefix internal names with underscores.

Only **Gmail REST API over HTTPS**, using `httpx`. No IMAP. Sequential downloads. No remote mutations. No deletion of archived messages.

Keep configuration, dependency declarations, documentation, and tests separate from application logic. Configuration is a flat TOML file with top-level keys only, parsed with the standard-library `tomllib`; no Python, JSON, YAML, or INI config parsing.

Do not support old archives when a format changes (file or directory names, layout, sidecar or `account.json` keys). The script handles only the current format: no compatibility readers, migration or upgrade code, or version branches. An existing archive is converted by hand, outside the script, before the new version runs.

Review minimality by checking whether a simpler clear approach meets the same requirements. Do not claim mathematical proof that no smaller correct program exists.

## Invocation and authentication

Run `python micro_gmail_backup.py [account-email]` with an optional `etc/config.toml` in the script directory; the `MICRO_GMAIL_BACKUP_CONFIG` environment variable overrides its path (tests must set it so they never read the real config). `etc/config.sample.toml` is the tracked template; the rest of `etc/` stays out of source control through a `.gitignore` negation rule. Unset paths default to the script directory, and relative config paths resolve against it, never against the current directory: `etc/client-secret.json` for the client secret, `tmp/` for scratch space when needed, `archives_dir` defaulting to `backups/`, `auth_dir` defaulting to `etc/auth/` and `logs_dir` defaulting to `logs/`. The per-account archive (`<archives_dir>/<account-email>/`), token file (`<auth_dir>/<account-email>.json`) and log file (`<logs_dir>/<account-email>.log`) are composed at the usage site by appending the account email, so each account gets its own subdirectory, token and log. The account email comes from argv or `config.toml` and is required. It is lowercased before any path is built, because Gmail addresses are case-insensitive and a second spelling must not create a second archive or token; dots in the local part are left alone, since Workspace addresses do not ignore them. Configuration lives in beartyped dataclass fields with the defaults declared on the fields themselves; `config.toml` values, when the file exists, are loaded over them onto the instance. There is no separate defaults dict. All procedural logic lives on one beartyped dataclass, MicroGmailBackup, holding the configuration fields, the implementation methods, and any run state; there are no dict-passing helpers and no split between config and session objects. Secrets and token files stay outside the archive and source control.

Use a Google installed-application OAuth token with `gmail.readonly`. The script performs the browser consent flow itself (localhost callback) only when the token file does not exist, using the client-secret file from `config.toml` or its default location, then saves the token atomically with owner-only permissions. If that client-secret file is missing, it fails before consent with a message naming the path and pointing to the README setup steps. The consent request passes the configured account as `login_hint`, so the browser preselects that account. A token whose profile belongs to another account fails with a message naming both accounts and telling the user to delete the token file and run again. Any other token problem (unreadable file, invalid JSON, wrong shape, expired without refresh token) crashes loudly; only a missing file leads to consent. Refresh expired credentials through Google's credentials library inside the request retry loop: the first request refreshes an expired stored token, and a network failure during any refresh retries like other network errors.

Check `users.getProfile` against the configured account before processing mail. Refuse a mismatch. Do not print tokens, response bodies containing credentials, or credential representations.

Use finite network timeouts. Five failure classes retry against a time budget per request (default 3600s, configurable via `retry_budget_seconds` in `config.toml`): `network_error` (transport failures with no HTTP response, including during a token refresh, DNS failures and rejected TLS certificates) retry until an HTTP response arrives, each retry logging the error's type and text; `quota_exceeded` (HTTP 403 whose first error reason is rateLimitExceeded or userRateLimitExceeded, the per-minute limits Gmail's error guide says to back off on, read and matched as Google's API client does; daily or other quota reasons are fatal because they do not clear within the budget) retry while responses stay `quota_exceeded`; `server_error` (HTTP 429 or any 5xx, which Gmail's error guide says to retry with exponential backoff) retry while responses stay server errors; `token_expired` (any HTTP 401, which Gmail's error guide and Google's auth library both answer with a token refresh) refresh the credentials with the stored refresh token, save them atomically, and retry. `failed_precondition` (HTTP 400 whose first error reason is failedPrecondition, on `users.messages.get` only) retries while responses stay `failed_precondition`: Gmail returned it once in about 43,700 message downloads, and the same request returned 200 minutes later, so it is a transient backend failure despite its name; a 400 with any other reason, or on any other request, stays fatal. A class switch restarts the backoff: if a `quota_exceeded` streak breaks into a connection error, `network_error` retries begin from zero, and vice versa. Sleeps start at 1s, multiply by 1.5 each attempt, cap at 120s, and hold at 120s. The budget is checked only at the moment of failure: if already spent, fail immediately with no further request; otherwise sleep (even past the budget) and retry without re-checking after the sleep. Each retry attempt is logged with its class, attempt, wait, and a short reason, and each refresh is logged. A `quota_exceeded` retry names the exceeded limit and its current value from the error details Google attaches, and links to the project's Gmail quota page with the value that almost avoids these waits. Repeated 401s refresh and back off as often as needed until the budget is spent, so multi-hour outages survive several token expiries. When a class exhausts the budget, the whole run fails loudly — not a single message: log the exhaustion with the class and reason, then re-raise the last failure itself, so an HTTP failure is reported with its status, response headers and body like any other fatal HTTP error. A refresh rejected by Google (no refresh token, expired, revoked or invalid grant) is not transient: the run stops at once and logs one error, without a traceback, naming the token file to delete so the next run signs in again. Only six error classes exist: the five retry classes above and Deleted. Any error outside these classes — any other HTTP status, malformed data, local write error, identity mismatch, corruption — fails the whole run immediately with a traceback instead of continuing to other messages. Future classes may define message-only failure if specified, as Deleted did. Rerunning the script retries failed messages from the beginning.

## Files and the whole algorithm

```text
archive/
  .lock
  account.json
  listings/<timestamp-plus-unique-suffix>/
    labels.json
    page-000001.json
    page-000002.json
  messages/
    message-<gmail-id>/
      <gmail-id>.<sha256>.eml.zst
      metadata.json
```

1. Hold an OS advisory writer lock for the run. Bind the archive to the verified account in `account.json`, which holds only `account_email` and an integer `format` (currently 1; bump it, and add keys such as a backend name, only if a later format needs them); reject a different identity or format.
2. Save the account label ID/name mapping in the new run directory. Enumerate all messages with `includeSpamTrash=true`, `maxResults=500`, no query/filter, following every page token. Reject repeated tokens. Persist each successful page atomically before proceeding. Save its parsed response, request parameters, and observation time. An absent `messages` field may mean an empty result; malformed data and failed requests must never become empty results.
3. Finish the current enumeration before downloading any bodies. Collect the union of message IDs in **all saved listing pages**, including interrupted earlier runs. These pages are the durable acquisition obligations; do not add a separate pending database, ledger, or cursor. A malformed saved page fails loudly.
4. Process the IDs newest first, in descending text order of the hex IDs, which grow with arrival time, so a long first run saves recent mail early. Text order is time order only for IDs of equal length; mail that arrived before November 2004 has 15-digit IDs and is processed first, which is accepted. For each ID, use `messages/message-<gmail-id>/`. Only `message-*` entries in `messages/` are message directories; other files there (such as `.DS_Store`) are ignored, and older unprefixed directories are not supported. Verify its existing body and metadata, otherwise fetch `users.messages.get(format=raw)`. Validate that the returned ID matches the requested ID. Decode valid padded or unpadded base64url strictly, preserving the original MIME bytes, including attachments: only canonical text is accepted (fully padded or fully unpadded, no `+` or `/`, zero unused trailing bits), checked by re-encoding the decoded bytes. Compute SHA-256 over the uncompressed MIME bytes and compress once at Zstandard level 9 into an independent checksum-enabled frame named `<gmail-id>.<sha256>.eml.zst`. Store the response's metadata without its `raw` field in the adjacent `metadata.json`, together with raw byte length, SHA-256, acquisition time, the message data file name (`message_data_file`), and the message data format name (`message_data_format`, always `"eml.zst"`). The sidecar's `message_data_file` must equal the actual file name; a mismatch fails loudly. No older sidecar formats are supported: a sidecar missing keys or carrying any key outside the current schema fails loudly as corruption; it is never treated as incomplete and never silently upgraded. Require IDs and hashes to be canonical lowercase hexadecimal before constructing paths. Every message belongs to a thread, so `threadId` is required in listing entries and sidecars and is canonical lowercase hexadecimal too.
5. Publish the compressed body first and `metadata.json` last, using same-directory temporary files, file flush/fsync, atomic replacement, and directory fsync. Use the same atomic-write helper for JSON and tokens; tokens must remain private. `metadata.json` may be overwritten atomically; body files are retained under their hash-bearing names. An acquisition is complete only if the directory ID, filename ID/hash, metadata, full decompression, checksum, byte length, and computed SHA-256 agree. Reject truncated frames and trailing data. A corrupt published acquisition fails loudly and is preserved. A missing metadata file is incomplete and must be downloaded again; a body left without metadata is not checked and is simply overwritten by the new download. Metadata whose body is missing cannot come from an interrupted write, so it is corruption and fails loudly. If reacquisition produces a different hash, preserve the earlier body and publish the new body under its own hash and the new metadata; the verification that follows every download then finds a second body and fails loudly, because a changed message is unexpected. Do not add periodic body re-downloads solely to look for changes.
6. A message-specific HTTP error outside the retry classes is reported with its status, response headers, and response body, followed by the exception traceback, and stops the run nonzero; the next run retries it. A 404 on acquisition means the message was deleted from the server: recognize it as deleted-before-download at once, without retrying, since no 404 has ever been seen to clear within a run and the next run requests it again anyway. This is a normal recognized outcome, not a failure: log it plainly with its ID, no exception, no traceback. Deleted-before-download IDs do not fail the run and do not block exit 0; their saved listings remain as evidence. A previously downloaded message with a verified local pair that is absent from the current listing is classified as deleted-since-download and kept locally, never removed. The run ends by printing acquisition stats split into previously seen messages (known from earlier listings or local message directories: verified on disk — of which deleted-since-download but kept locally — downloaded now, deleted-before-download) and newly found messages (first observed in this run: downloaded now, deleted-before-download). The stats are printed also when acquisition stops on a crash or interrupt, before the cause is logged, after a warning that they cover only the messages processed so far; a run that succeeds ends with `backup completed`. Its saved listing remains an obligation on the next run, even if the message later disappears remotely. Fatal HTTP failures print the same response detail before their traceback. Any other crash after a response arrived (a non-JSON success body, or data that fails parsing or validation) logs the last response's URL, status, headers and body preview with its traceback. A crash while the current request attempt has no response — before the first request, in a token refresh, or in a send that fails, such as an undecodable body — logs the traceback alone, never an older response. Never print the request Authorization header. Every HTTP request logs one line before sending (method, full URL with query string, purpose — never headers or tokens) and one line after the response (status, full URL, purpose); httpx's own request log is silenced so each response is logged once; each quota-403 retry logs its attempt number and wait. The file log is `<logs_dir>/<account-email>.log` and can be overridden with the `MICRO_GMAIL_BACKUP_LOG` environment variable, a file path (tests must set it to a temporary path and never touch the real log). It starts once the configuration names the account, so errors before that (unreadable config, missing or invalid account email) reach only the terminal. Both handlers share one module-level log format. The log level is INFO; `MICRO_GMAIL_BACKUP_DEBUG=1` opts in to DEBUG lines with every response's headers and each error response's body. Collecting the previously seen IDs logs a line before and after, since reading every saved page takes a while. Progress lines carry their stage: `stage 1/2 [done/~expected]` per listing page, with the profile's `messagesTotal` as the expected count (only an estimate; real listings have ended slightly above it), then `stage 2/2 [done/total]` per message; acquisition ends with the acquisition stats above. Anything unexpected (malformed data, assertion failure, local write error, identity mismatch, corruption) crashes the run with a traceback, nonzero. An uncaught keyboard interrupt already exits nonzero. Exit zero only if enumeration and verification succeeded and every known obligation has a valid pair.

Never duplicate the same raw MIME in JSON or another payload file. Never remove saved evidence or local messages because they disappear from a newer listing. Include locally present message directories in verification so historical damage is detected even if an inventory file is missing. Verify the body the metadata references; any other body beside a complete pair fails loudly. Delete temporary files left by a crash: a message directory's before it is downloaded again, and the token's at run start.

## Deliberate limits

Labels are captured when a message is downloaded, with each run's label mapping and listing evidence retained. No metadata refresh for already downloaded messages. No mutable run-status documents, per-attempt audit journal, resumable partial-message transfer, or automatic repair of corruption. A failed message is retried from its beginning on a later invocation. Bounded retry of the five retry classes is the one allowed exception to the no-backoff rule.

A listing observes a changing mailbox; it is not an atomic snapshot. Messages removed before they were ever observed cannot be backed up. Saved pages preserve observed obligations, but no program can guarantee acquisition of bytes deleted remotely before download.
